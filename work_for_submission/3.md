# MindMeter 沟通管理与风险管理计划

> 项目：MindMeter（心智镜）｜团队：4 人｜周期：6 周｜阶段：分析 → 设计 → 开发 → 测试 → 发布 → 运维

## 一、沟通管理计划

说明：按生命周期组织；频度用“即时/每天/每周/里程碑”表示；产出物优先落到仓库文档、Issue、代码或可演示版本。

| 沟通内容 | 沟通频度 | 沟通方式 | 产出物 |
| --- | --- | --- | --- |
| 课程要求、评分标准与提交节点确认 | 即时/一次性 | 面对面 + 微信群 | 需求清单、提交检查表 |
| 用户访谈与认知测评需求调研 | 每天/按需 | 线上访谈、问卷 | 访谈纪要、需求列表 |
| 产品范围、4 个游戏规则与指标定义 | 每周 | 周会 + 文档评审 | 需求文档、游戏规则表 |
| 竞品对比与差异化确认 | 一次性 | 文档 + 群讨论 | 竞品对比表、定位陈述 |
| 6 周计划、任务拆分与分工 | 一次性 + 每周更新 | 周会 + GitHub Issues | 里程碑计划、任务清单 |
| 低保真原型与页面流程评审 | 每周 | 视频会议 + 原型链接 | 原型、评审意见 |
| 技术选型、目录结构与数据格式 | 一次性 | 技术评审 + 文档 | 技术方案、数据 schema |
| 视觉规范、报告模板与文案 | 每周 | 微信群 + 共享文档 | 设计稿、文案定稿 |
| 每日进度、今日任务与阻塞 | 每天 | 微信群文字 | 三行站会记录、阻塞清单 |
| 接口联调、计分逻辑与游戏参数 | 每天/按需 | 语音会议 + Issue | 联调记录、计分说明 |
| 代码评审与合并 | 每次 PR | GitHub Pull Request | 评审意见、合并记录 |
| 需求变更/砍功能 | 即时 | 微信群 + Issue | 变更记录、更新后的任务 |
| 测试计划、用例与验收标准 | 每两周/里程碑 | 文档 + 评审会 | 测试用例、验收清单 |
| 缺陷跟踪与修复 | 每天 | GitHub Issues | 缺陷列表、修复记录 |
| 用户测试与反馈收集 | 每周/按计划 | 线上测试 + 访谈 | 用户测试报告 |
| 上线部署与演示彩排 | 即时（发布前） | 群 + 视频会议 | 上线清单、演示脚本、备用视频 |
| 答辩材料与课程提交 | 即时（发布阶段） | 线下/视频会议 | 答辩 PPT、演示视频、文档包 |
| 线上问题与版本回滚 | 即时 | 微信群 + Issue | 处理记录、回滚记录 |
| 数据清除/隐私相关请求 | 即时 | 微信群 + 文档 | 处理记录 |
| 项目复盘与经验总结 | 即时（项目结束） | 线下会议 | 复盘记录、改进项 |

**沟通注意事项**：

- 每天站会只讲三件事：昨天做了什么、今天做什么、有没有阻塞；
- 周会不超过 30 分钟，必须产出“谁、做什么、什么时候完成”；
- 重要结论 24 小时内回写 `docs/` 或 GitHub Issue，聊天记录不作为最终依据；
- 新增功能或延期必须 4 人确认，不能两个人私下改范围；
- 答辩前 3 天冻结功能，只修 bug。

## 二、风险管理计划

说明：只跟踪会影响 6 周交付的风险；影响程度用“高/中/低”，优先权用“高/中/低”，跟踪频率用“即时/每天/每周/每月”。本计划同时关注单个风险和整体项目风险，也关注正面机会（如报告传播带来种子用户）。

| 风险名称 | 所属维度（资源、项目管理、外部因素、技术、进度） | 风险说明 | 影响程度（重要性） | 对工作量的影响（高、中、低） | 对进度和成本的影响（高、中、低） | 优先权（紧急程度） | 跟踪频率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 范围过大 | 项目管理 | 4 个游戏 + 报告 + 账号/支付/后台都想做，6 周做不完，最后核心功能缺失 | 高 | 高 | 高 | 高 | 每周 |
| 进度延期 | 进度 | 某个游戏或报告卡住，W3/W4 里程碑延迟，影响 W6 答辩 | 高 | 高 | 高 | 高 | 每周/每天 |
| 计分与常模被质疑 | 技术 | 参考分缺少常模和效度证据，用户或老师质疑“不准”，影响可信度 | 高 | 中 | 中 | 高 | 每周 |
| 游戏太难或看不懂 | 技术 | 说明不清、练习不足、参数太难，用户中途退出，完成率低 | 高 | 中 | 中 | 高 | 每周 |
| 用户测试样本不足 | 外部因素 | 校园渠道招募不到 10–15 名测试用户，反馈不足，问题发现太晚 | 中 | 中 | 中 | 中 | 每周 |
| 刷新/误关导致数据丢失 | 技术 | 只存内存或写入失败，用户刷新后结果丢失，演示翻车 | 中 | 中 | 中 | 中 | 每天（测试期） |
| 手机/浏览器兼容问题 | 技术 | 不同浏览器或小屏幕布局错位、按钮点不到，影响测评完成 | 中 | 中 | 中 | 中 | 每周 |
| 分工不清/互相等待 | 资源 | 任务没有唯一负责人，接口对不上，出现重复劳动或空等 | 中 | 中 | 中 | 中 | 每周 |
| 成员时间投入不足 | 资源 | 课程/实习冲突导致某成员连续缺勤，关键模块无人接手 | 高 | 高 | 高 | 高 | 每周 |
| 答辩现场故障 | 外部因素 | 网络、设备或部署平台故障，线上链接打不开，演示中断 | 高 | 低 | 高 | 高 | 发布前即时 |
| 部署平台/第三方服务故障 | 外部因素 | 静态托管、CDN 或依赖服务不可用，短时间无法访问 | 中 | 低 | 中 | 中 | 发布期每天 |
| 隐私/伦理表述不当 | 项目管理 | 文案出现“诊断/治疗/提升智商”，或收集了不必要的身份信息 | 高 | 低 | 中 | 高 | 每周 |

**重点风险应对**：

1. **范围过大**：W1 写死“4 游戏 + 报告 + 本地历史”；账号、支付、后台、AI 全部不做；W3 结束必须至少 2 个游戏可玩；新增功能先删一个旧功能。
2. **进度延期**：每周五必须演示可运行版本；W5 留缓冲；W6 冻结功能只修 bug；延期时优先保测评和报告，砍分享、历史趋势。
3. **计分被质疑**：统一叫“课程演示参考分”，不叫智商/临床测评；公式和阈值写在代码与文档里；报告明确“非常模、非临床”；不伪造信效度数据。
4. **答辩故障**：准备线上版 + 本地版 + 录屏视频 + 手机热点；提前 30 分钟到场；演示只走稳定路径。

## 三、风险跟踪机制

- 每周一例会花 10 分钟过一遍风险表：有没有新风险、等级是否变化、应对是否完成；
- 每周五演示后更新状态：开放 / 缓解中 / 已关闭；
- 出现以下情况立即升级：里程碑延迟超过 1 天、核心成员连续 2 天无法投入、线上演示环境不可用、出现隐私/伦理问题；
- 风险关闭后保留记录，答辩时可说明“识别过、处理过”。
