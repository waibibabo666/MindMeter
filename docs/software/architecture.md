## 二、核心技术选型

### 2.1 前端方案对比

| 维度 | A 原生 JS（无构建） | B Vite + React | C Vite + Vue | D Next.js | E 小程序 |
| --- | --- | --- | --- | --- | --- |
| 学习成本 | 低 | 中 | 中 | 高 | 中高 |
| 构建部署 | 无需构建 | 需构建 | 需构建 | 需 Node 运行时 | 需开发者工具 |
| 运行时体积 | 0 | 约 140KB gzip | 约 100KB gzip | 更大 | 受平台限制 |
| 毫秒级计时适配 | 好（直接操作 DOM） | 一般（状态驱动渲染） | 一般 | 一般 | 一般 |
| 状态复杂度是否匹配 | 匹配 | 过剩 | 过剩 | 过剩 | 不适用 |
| 演示风险 | 低（双击可开） | 中（构建失败） | 中 | 高 | 高（审核） |

### 2.2 结论：选 A

三条理由按重要性排序：

1. **这套产品的技术核心是计时，不是渲染。** 抑制控制与加工速度依赖毫秒级反应时，React 的状态更新会引入不可控的渲染延迟，测量点反而更难界定；直接操作 DOM + `performance.now()` 更可控。
2. **页面数量不足以产生框架收益。** 全部交互 6 个屏，没有路由嵌套、没有跨页共享状态——框架主要解决的问题在这里不存在。
3. **答辩现场最怕构建失败。** 静态文件可以拷到任何机器双击打开，是最硬的兜底。

**允许的例外**：若 W4 发现页面复用不可维护，可局部引入 Vite 做打包，但不换框架，计分模块不动。

### 2.3 存储选型

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| `localStorage` | ✅ 采用 | 同步、简单、容量（约 5MB）足够存数十次测评 |
| IndexedDB | ❌ 不用 | 异步 API 复杂度高，存储量需求远未到 |
| 后端数据库 | ❌ 不用 | 需要账号体系，与"不收集身份信息"冲突 |

**注意**：为支持"行为叙事"，需存**试次级数据**（每次试次的正确与否、反应时），不是只存聚合分。一次测评约几百条记录、几十 KB。

### 2.4 部署

静态托管（GitHub Pages 优先），保留每周演示版本 tag 以便回滚；断网时用本地文件 + 录屏兜底。

## 三、系统架构

### 3.1 模块划分

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `pages` | 首页、同意、说明、报告、历史 | 不写计分公式 |
| `games` | 四个游戏的试次控制与指标采集 | 不判定分数 |
| `core_engine` | 计分、分档、配置版本 | 不碰 DOM、不发请求 |
| `ai` | 表达层：叙事、追问、计划 | 不改分数、不改结论集合 |
| `templates` | 模板文案与建议库 | 不含逻辑 |
| `storage` | 读写本地记录，异常处理 | 不上传 |

### 3.2 数据流

```text
游戏 → 原始指标 → core_engine 计分 → 分档与 facts
                                    ↓
                        ┌───────────┴───────────┐
                        │   AI 开关（默认关）    │
                        └───┬───────────────┬───┘
                        关 │               │ 开
                      模板渲染          模型 → 校验 → 通过则用
                        │               │ 失败
                        └──────→ 模板 ←─┘
                                    ↓
                              报告页 / 历史
```

## 四、AI 技术方案（论证部分）

### 4.1 五种候选

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A 纯模板 | 固定文案套变量 | 作为兜底保留 |
| B 单次结构化生成 | 分数直接丢给模型，输出整段 | 不可控，弃 |
| **C 规则定结论 + 模型只表达** | 结论与建议由规则产出，模型只改写文字 | ✅ 采用 |
| D 多 Agent 流水线 | 规划→分维→审稿→汇总 | 6 周做不完 |
| E 对话教练 | 多轮 + 记忆 + 工具 | 降级为 P1 的追问功能 |

### 4.2 为什么是 C

1. **可复现**：分数、分档、建议集合全部由确定性代码产出，同输入同输出；
2. **可追溯**：每条建议带 ID，能映射回维度与规则；
3. **可解释**：答辩时能指着代码说"这条建议为什么出现"；
4. **可降级**：模型失败时，A 方案就是完整产品。

### 4.3 两种接入形态

| 形态 | 是否需要后端 | 适用 | 特点 |
| --- | --- | --- | --- |
| A 纯静态 | 否 | 快测、标准档、断网演示 | 模板随代码发布，运行时零请求 |
| B serverless 网关 | 是（单函数） | 深度档解读、追问 | key 不在前端，只转发不落库 |

先做 A，W4 视进度决定是否上 B。

### 4.4 质量保障

- 五条核心校验：结构合法、建议 ID 在池内、数字来自 facts、禁用词 0、长度达标；
- 生成后自检一次（模型审自己的稿）；
- 强制模板五种情况：无可信结论、数据不足、间隔过短、危机词、超时；
- 记录版本号、模型名、是否降级。

## 五、关键技术风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 移动端点击延迟 | 污染反应时 | `touch-action: manipulation`，统一用 `pointerdown` |
| 后台标签页节流 | 试次错乱 | 监听 `visibilitychange`，切回时重置当前试次 |
| `localStorage` 不可用 | 静默丢数据 | 全部写入包 `try/catch`，失败明确提示 |
| 模型幻觉 | 编造数字与建议 | 数字集合比对 + 建议 ID 校验 + 模板兜底 |
| 常模缺失 | 无法给百分位 | 只做自身前后对比，不做人群比较 |
| 演示现场断网 | 页面打不开 | 本地版本 + 录屏，报告不依赖网络 |
