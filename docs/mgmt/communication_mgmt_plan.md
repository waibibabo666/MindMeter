## 二、目的与原则

4 个人、无固定 deadline、产品化推进。沟通目标不是“开很多会”，而是让每个人知道：**当前阶段做什么、卡在哪里、什么时候能演示**。

- 阶段制：M0 设计 → M1 纵向切片 → M2 完整测评 → M3 产品化；
- **先纵向切片**：账号 + 标准 4 项 + 服务端计分 + 对话 + 记忆 + RAG + 趋势，跑通再铺功能；
- 每周有可运行增量；
- 重要决定回写文档/Issue，不只留在聊天；
- 阻塞超过 1 天升级；
- Agent/模型/隐私相关改动必须 4 人确认。

## 六、任务与决策

- 任务统一放 GitHub Issues：负责人、验收、阶段；
- 涉及“加功能/换架构/延期”的决定，4 人确认；
- 架构口径：FastAPI + Postgres/pgvector + LangGraph + 原生前端；BYOK 加密存库；服务端计分；不上 K8s/Redis/Milvus；
- 任何回退到 L1（无账号/无后端/客户端计分）的提案，必须重新评审；
- 新增 Agent 能力必须先定义校验/降级/评测，不能只写 prompt。

## 七、升级机制

| 情况 | 找谁 | 时限 |
| --- | --- | --- |
| 任务卡住 | 对应负责人 | 当天 |
| 阶段延迟 | 项目负责人 | 当天调顺序/砍范围 |
| 方案冲突 | 项目负责人组织 15 分钟会 | 24 小时 |
| 隐私/Key/越界问题 | 项目负责人 + 技术负责人 | 立即 |
| 模型/RAG 质量不达标 | xlr268 + 1213lz | 当天决定降级/换方案 |

## 八、交付与交接

- 每个阶段有可运行版本；
- 代码合并前至少 1 人评审；安全/计分/Agent 校验 2 人；
- M3 交付：API 服务、Postgres、前端、文档、运行手册、备份/恢复说明；
- 课程提交版只作历史快照，不随 L2 代码更新。
